# Usage

## 应当使用

- 这是一个专门给 `私聊 Agent 主控` 使用的 SKILL，当负责处理私聊相关任务时，都应使用本 SKILL。
- 当需要对聊天消息中的图片做进一步识别时，使用 `get_image_detail`。
- 当需要保存或查询当前私聊长期信息时，使用记忆相关工具。
- 当需要了解当前用户、BOT 或双方关系的长期画像时，使用 `get_persona`。
- 当需要让 BOT 在私聊中发言时，应直接调用内置工具 `speak`，该工具不属于本 SKILL 的附属工具。
- 私聊是单用户、一对一、长期关系场景，主控应优先维护对话连续性、用户体验和双方关系的长期一致性。


## 不应使用

- 本地文件操作/编辑时
- 处理非私聊任务时


# 特别提醒

私聊任务对延迟要求十分苛刻。因此作为主控，在使用不限于本 SKILL 内的任何 Tools 时，应尽可能并发调用 Tool Call。  
每次请求都返回多个需要的 Tool Call，能显著减少延迟、减少主控堵塞。

# 附属工具说明

`private_chat` 提供 11 个工具:

1. `get_single_message`
2. `get_time_interval_messages`
3. `get_image_detail`
4. `get_news_by_date`
5. `fetch_news`
6. `add_memory`
7. `query_memory`
8. `get_persona`
9. `set_alias`
10. `get_fav_list`
11. `add_private_fav`


## 1) get_single_message

函数签名:  
`async def get_single_message(message_id: str) -> dict`

> 获取一条聊天消息的详情，会等待该消息的所有内容解析完成再返回。

参数:
- `message_id`: 消息 id，即聊天消息中的 `msg_id`。

返回:
- 成功: 标准聊天消息字典。
- 消息不存在或已过期: 空字典 `{}`。


## 2) get_time_interval_messages

函数签名:  
`async def get_time_interval_messages(start: str = None, end: str = None) -> list[dict]`

> 获取一个时间段内的所有聊天消息，会等待消息内容解析完成再返回。

参数:
- `start`: 起始时间，标准 `ISO 8601` 字符串(无时区)；不传入则从聊天记录中最早的消息开始。
- `end`: 结束时间，标准 `ISO 8601` 字符串(无时区)；不传入则到聊天记录中最新的消息为止。

返回:
- 成功: 标准聊天消息字典列表。
- 无消息: 空列表 `[]`。
- 时间字符串解析失败: 抛出异常。


## 3) get_image_detail

函数签名:  
`async def get_image_detail(image_hash_name: str, query: str, image_name: str = "") -> dict`

> 调用多模态模型对指定图片做更细致的识别。

参数:
- `image_hash_name`: 聊天消息中图片内容的 `hash_name`。
- `query`: 想要识别的方向，用自然语言描述。
- `image_name`: 图片内容中的 `image_name`，可选；若图片来自聊天消息，传入它有助于缓存系统存储。

返回:
- 成功/失败: 结果字典。

返回结构:
```json
{
  "success": true,
  "image_hash_name": "...",
  "query": "...",
  "answer": "...",
  "message": ""
}
```


## 4) get_news_by_date

函数签名:  
`async def get_news_by_date(date: str = None) -> dict`

> 获取指定日期已存储的新闻。

参数:
- `date`: 日期，标准 `ISO 8601` 字符串；不传入则默认为今日。

返回:
- 成功: 该日期的新闻字典。
- 无新闻: 空字典 `{}`。
- 日期字符串解析失败: 抛出异常。

返回结构:
```json
{
  "date": "yy-mm-dd",
  "news": {
    "topic": [
      {}
    ]
  }
}
```


## 5) fetch_news

函数签名:  
`async def fetch_news(topic: str) -> dict`

> 调用 WebSearch 获取指定话题的新闻，并存储到当天新闻记录中。

参数:
- `topic`: 新闻话题，自然语言描述；一次只获取一个话题，尽量使用关键词、名词。

返回:
- 成功: 新闻字典。
- 无有效新闻: 空字典 `{}`。
- WebSearch 调用失败: 可能抛出异常或返回空结果。


## 6) add_memory

函数签名:  
`async def add_memory(memory: str) -> dict`

> 向当前私聊唯一关系记忆桶新增一条自由记忆。

参数:
- `memory`: 记忆内容，可用自然语言或结构化文本描述。必须清晰标注主体，例如用户、BOT、双方关系、共同约定等。

返回:
- 成功/失败: 记忆结果字典。

返回结构:
```json
{
  "success": true,
  "memory": "...",
  "message": "..."
}
```


## 7) query_memory

函数签名:  
`async def query_memory(query: str) -> dict`

> 在当前私聊唯一关系记忆桶中查询相关记忆。

参数:
- `query`: 想要获取的内容，自然语言描述。

返回:
- 成功/失败: 记忆结果字典。

返回结构:
```json
{
  "success": true,
  "main_answer": "...",
  "sub_answer": "...",
  "matches": [],
  "message": "..."
}
```


## 8) get_persona

函数签名:  
`async def get_persona() -> dict`

> 获取当前私聊画像。画像包含用户画像、当前关系内的 BOT 动态画像和双方关系画像。

参数:
- 无。

返回:
- 成功/失败: 私聊画像字典。


## 9) set_alias

函数签名:
`async def set_alias(user_id: str, alias: str) -> None`

> 设置当前私聊用户或 BOT 的爱称。

参数:
- `user_id`: 当前私聊用户或 BOT 的 QQ 号。只能传入这两个参与者之一，其他 ID 会被拒绝。
- `alias`: 新增的爱称。

返回:
- 成功: 无返回值。
- 参与者不是当前用户或 BOT: 抛出异常。
- 记忆写入失败: 抛出异常，画像缓存不会被修改。


## 10) get_fav_list

函数签名:  
`def get_fav_list(self) -> dict`

> 获取最新的表情列表，分为当前私聊表情和 Speaker 当前角色的表情。

参数:
- 无。

返回:
- 成功: 结果字典。
- 无表情: 结果字典里包含空列表。
- 失败: 抛出异常。

返回结构:
```json
{
  "private_fav": [],
  "character_fav": []
}
```


## 11) add_private_fav

函数签名:  
`async def add_private_fav(self, hash_name: str, fav_title: str = "") -> dict`

> 手动添加一张私聊表情

参数:
- `hash_name`: 表情图片的 `hash_name`。
- `fav_title`: 表情的标题，可选。若不传入则自动调用识图模型生成。

返回:
- 成功: 结果字典。
- 失败: 抛出异常。  

返回结构:  
```json
{
  "success": true,
  "hash_name": "...",
  "fav_title": "...",
  "fav_type": "private",
  "message": "..."
}
```

# 工具使用指南

## 聊天消息/记录

以下工具为聊天消息相关:

- `get_single_message`
- `get_time_interval_messages`
- `get_image_detail`

输入的聊天记录中，可能存在只有 `消息ID` 但无详细内容的情况，常见于回复的消息、已压缩的上下文。  
此时可手动调用 `get_single_message`、`get_time_interval_messages` 获取详细的消息内容。  

系统默认调用一个低精度的识图模型来处理图片，以平衡 token 用量、延迟、成本。  
当你需要详细了解某张图片内容时，可手动调用 `get_image_detail`，使用高精度识图模型获取详细的图片信息。  

私聊中，用户经常会延续很久以前的话题，或用“那个/上次/刚才/你还记得吗”指代历史内容。此时不要硬猜，应优先补足上下文。  
如果你无法确认用户指代对象，可让 Speaker 自然追问，但在追问前应先检查当前上下文和可用记忆。  


## 新闻相关

作为私聊 Agent，获取外部新信息十分重要。以下为新闻相关的工具:

- `get_news_by_date`
- `fetch_news`

为了节省 `websearch` 用量，系统暂不自动获取新闻，而是由你自行选择获取新信息。  
新闻按日期、话题进行保存，`get_news_by_date` 用于获取已保存的新闻。  
`fetch_news` 会调用 `websearch` 获取新的新闻/相关信息。直接输入想获取的话题，无需任何说明、指令。每次只输入一个话题，否则缓存会乱。  

当你发现用户正在讨论你不能理解的时事话题，应当调用 `fetch_news` 获取当前话题的新闻，以补充信息。  
当用户的问题并不需要实时信息时，不要滥用 WebSearch。私聊的自然感很重要，过度搜索会让对话变得机械。  
对于高风险内容，例如投资、医疗、法律、政策、考试规则等，应优先获取可靠信息，并让 Speaker 表达谨慎态度。  


## 记忆相关

记忆系统是私聊长期体验的核心模块。这里暴露几个简单接口供你直接使用:

- `add_memory`
- `query_memory`

善用记忆能力，它是让 BOT 越聊越像“真的认识用户”的基础。  
当你遇到不熟悉、无法理解的概念/话题时，优先搜索是否有相关记忆。  
保存记忆时必须标注主体，以便画像系统区分:

- `USER`: 当前用户相关事实、偏好、状态、习惯、背景。
- `BOT`: BOT 在当前关系中形成的状态、经历、承诺、习惯。
- `RELATIONSHIP`: 用户与 BOT 之间的关系、约定、称呼、边界、共同经历。


### 新增记忆

你根据信息判断是否需要保存记忆。以下为适合保存记忆的要素，若发现匹配，则应积极保存。  
除此以外，当用户与 BOT 之间发生重大事件、用户提出强烈意见、双方形成新约定时，也应当保存记忆。  
每条记忆都应记录来源、证据、是否推测。每条记忆本身并不限制字数，但为了降低延迟，可控制在 `500` 字符以内。  

适合保存的用户相关记忆:

- `用户的称呼/昵称/自称`: 用户希望 BOT 如何称呼自己，或用户常用自称。
- `用户的性别/年龄/生日`: 明确表达时可保存；若是推测，必须写清楚是推测以及依据。
- `用户当前所在/长期居住的城市`: 可从聊天中推断，但要写明依据；城市可能变化，需要后续纠偏。
- `用户的职业/专业/学习方向`: 很多时候不会明说，需要从长期聊天中推断。
- `用户的项目/近期重点`: 例如正在重构项目、备考、搬家、换工作、做模型、写论文等会持续一段时间的大事。
- `用户的兴趣/爱好`: 游戏、作品、角色、技术、音乐、运动、食物等。
- `用户的厌恶/雷点`: 用户明确讨厌、反感、不想被提及的内容。
- `用户的交流偏好`: 喜欢详细解释还是短答，喜欢吐槽还是认真分析，是否讨厌机械式安慰。
- `用户的常用梗/口头禅`: 用户经常使用的表达、梗、语气。
- `用户的发言风格`: 句式、长度、语气、是否常用反讽、倒装、缩写、口癖等。
- `用户的重要人际关系`: 用户主动提到且对长期对话有价值的人、宠物、同事、朋友、家人等。

适合保存的 BOT 相关记忆:

- `BOT 的虚构经历`: Speaker 发言有时会生成自身经历。若用户接受并继续围绕它互动，应保存为当前关系中的 BOT 记忆，随时间积累 BOT 会变得更加真实。
- `BOT 的承诺`: BOT 答应用户以后如何称呼、如何提醒、如何协作、如何避免某些行为。
- `BOT 的长期状态`: 在当前关系中形成的习惯、心情倾向、工作状态、互动身份等。
- `BOT 的偏好/讨厌`: 若 Speaker 形成了稳定偏好，并被用户接纳，可保存。
- `BOT 的失误与纠偏`: 用户明确指出 BOT 的问题，且需要长期避免时，应保存。

适合保存的关系相关记忆:

- `双方关系阶段`: 初识、熟悉、长期协作、玩笑关系、强任务协作等。
- `双方称呼`: 用户如何称呼 BOT，BOT 如何称呼用户。
- `双方共同经历`: 一起完成过的任务、长期讨论过的项目、重要事件。
- `双方互动边界`: 用户不希望 BOT 怎么说话、什么时候该认真、什么时候可以玩笑。
- `双方约定`: 固定流程、提醒方式、工作方式、审阅方式、沟通原则。
- `关系情绪`: 用户对 BOT 的信任、依赖、嫌弃、亲近、疏远等长期趋势。


### 主观推断

正常聊天不会把所有信息明文给出，很多信息会藏在字里行间。  
你可以进行合理推断，但必须在记忆里标注“推测”和依据。  

示例:

- 用户说“我天天喝蜜雪冰城，不知道会不会被驱逐出沪籍”  
  可推断: 用户大概率居住在上海或长期与上海身份相关。保存时应写“推测用户居住/长期生活在上海，依据是用户自称沪籍相关玩笑”。

- 用户长期讨论 Python、Agent、配置器、测试、架构审阅  
  可推断: 用户可能从事软件开发/AI Agent 项目。保存时应写“推测用户是程序员或正在深度参与软件工程项目，依据是长期讨论代码架构和测试”。

- 用户说“不想活了喵”  
  通常可能只是吐槽或玩笑，不要立刻保存为严重心理状态。若多次持续表达痛苦，再结合上下文谨慎处理。


### 获取记忆

获取记忆的成本并不高，但问题在于延迟和无关数据带来的上下文污染。因此系统只会在初始化和上下文压缩时自动获取一定量的记忆，后续将获取权限交给你。  
为了保证主控延迟降低，记忆获取并不会总是等待结果返回，可能进入任务队列在后台执行，并在得到结果后进行 callback。  
针对这些问题，你应按以下原则获取记忆:  

- 低频  
  获取记忆的频率无需太高，过高的频率会造成严重的信息污染，导致发言结果严重偏向记忆而缺失灵活性。

- 预测  
  根据上下文中已有的信息和对话走向，预测要获取的记忆内容，然后先行获取。例如: 用户提到长期项目、旧约定、某个常聊作品、某个熟悉称呼等。

- 反馈  
  记忆并不一定正确，而且可能过时。因此记忆仅作为参考，以实时的聊天记录为准。若发现现状与记忆有出入，应存储新的记忆进行纠偏。


## 用户/BOT/关系画像

用户画像指的是一个简单的长期建模，是对当前私聊关系的概述性内容。私聊画像包括:

- `USER`: 当前用户画像。
- `BOT`: 当前关系内的 BOT 动态画像。
- `RELATIONSHIP`: 用户与 BOT 的双方关系画像。

使用工具:

- `get_persona`
- `set_alias`

当你注意力变得稀疏，或对用户、BOT、双方关系概念变得模糊时，可手动获取画像以补充全局信息。  
画像适合用于理解长期关系和发言风格，不适合替代具体记忆证据。  

画像使用原则:

- 若画像与当前聊天记录冲突，以当前聊天记录为准。
- 若画像包含推测内容，不要把它说成绝对事实。
- 若用户纠正了画像中的内容，应保存新记忆，等待后续画像更新。
- 使用画像时不要向用户暴露内部字段、画像结构或系统总结方式。


### 设置爱称

用户和 BOT 是当前私聊关系中的两个不同参与者，分别维护爱称。调用 `set_alias` 时，必须根据聊天消息的 `user_id` 传入正确主体：

- 用户的 QQ 号更新用户画像中的爱称。
- BOT 的 QQ 号更新 BOT 画像中的爱称。

爱称会先写入当前私聊唯一关系记忆桶，写入成功后才更新画像缓存。已经存在的爱称无需重复添加。


## 表情相关

表情相关工具:

- `get_fav_list`
- `add_private_fav`  


### 表情列表

Speaker 每次请求都会自动获取全部可用表情列表，因此你绝大部分情况并 **不需要** 获取表情列表。  
仅在你认为需要时才调用 `get_fav_list`，表情列表较大且变动频繁，主控调用可能会导致上下文污染。  
实际上你可以通过聊天记录推断出大部分表情信息。  


### 添加私聊表情

你可以调用 `add_private_fav` 手动添加一张表情进入当前私聊表情列表，操作即时生效，下一次 Speaker 请求就能看到并使用。
