## 1. 结论与建议

**确实有需要清理的测试债务，但目前更突出的是接口失配、运行隔离不足和组织混乱；还不足以支持“大量测试可以直接删除”。**

建议先做三件事，再决定删减范围：

1. **对齐已经失配的测试契约。** AutoMapping 两个文件的 21 个用例全部失败，且包含已经不存在的方法；配置测试还保留着旧的缺省返回值预期。先确认现在打算支持什么行为，再更新测试或修复实现。
2. **让默认测试在干净环境里可靠运行。** 去掉 mock 测试对本地配置的依赖，排查整套运行才出现的私聊回收超时。否则后续移动、合并测试时，很难区分整理引入的问题和原有问题。
3. **按业务域整理文件，共享确实重复的构造代码。** 保留并发、存储迁移、数据完整性和故障恢复回归；分别处理源码结构约束、重型用例、手工实测和历史实验数据。

不建议按文件短小、名称含 `v3`/`v4`/`refactor`、长期没修改或使用 mock 就判定过期。审查中也没有证明整批行为测试在重复验证完全相同的场景。

## 5. 过期与低收益候选：具体判断

### 5.1 已确认失配，优先对齐契约

**AutoMapping 两个测试文件。** 当前代码提供 `flush()`/`flush_async()`，初始化通过 executor 异步完成；测试还期待旧方法、旧构造方式以及构造后立即可用的数据。测试最后变更于 2026-09-06，而实现之后仍在修改。

建议逐项确认：初始化完成的公开等待方式、持久化屏障、无路径内存模式是否还支持、迁移失败在哪里暴露、序列化异常何时发生。明确后再改用公开接口验证。`_write_batch` 这类私有实现断言可替换，但“失败后数据不丢失”“重载后数据正确”等行为不能随接口一起删掉。**单凭代码没有某个方法，还不能证明删掉相应产品能力是正确的决定。**

**配置缺省行为。** `tests/test_config_core.py:488` 仍断言 `get_llm("missing") == {}`，而 `src/TIYA/config.py` 当前会抛出 `KeyError`。若抛错是现在的设计，就更新这一契约；如果仍要求缺省返回值，应修复实现。这个差异明确，适合小范围处理。

两者合计约占总墙钟时间的两成；只是单次本机测量，不是稳定性能基准。另有 HTTPX、DeepSeek、WebSearch 构建等累计成本，不能仅凭耗时推断发起了真实外网请求。

建议**按具体用例标记重型验证**，不要把整个 `*_performance.py` 文件排除：这些文件中还包含快速的批处理次数、线程位置和结构约束测试。日常开发可按业务目录选择相关回归，提交前保留完整离线验证。是否拆分频率，应在稳定基线后决定。

对 `test_alias_async_performance.py` 的 `max(loop_gaps) < 0.06`、`test_auto_mapping_sqlite.py` 的 `elapsed < 0.1` 等墙钟断言，建议检查是否可改为事件同步、调用计数或线程归属；时序阈值应有明确依据。本次没有实测证明它们发生抖动。

## 8. 本地实验数据应单独制定处理清单

`tests_data/` 中同时存在输入样本、报告多个版本、截图、数据库及 WAL/SHM、缓存压缩包、下载的第三方源码和 Agent 工作目录。默认 `tests/` 与生产 `src/` 的 Python 文本检索均未发现 `tests_data` 路径引用；部分手工脚本明确使用其中数据。

因此，可将它作为独立清理对象，但本次静态检索**不能证明没有动态路径或人工用途**，也不能把正在开发的 Agent 实验目录直接当垃圾。

建议后续先按以下用途建清单，再处理：

| 类型 | 处理原则 |
|---|---|
| 仍需重复使用的最小输入样本 | 绑定具体测试/脚本；需要共享的样本明确纳入版本管理 |
| 可再生成的截图、报告、缓存和基准输出 | 单独放输出目录，保留生成入口；确认不用后再清理 |
| 历史实验存档与多轮方案报告 | 按实验归档，并记录结论或对应开发任务 |
| 当前人工实测的持久化状态 | 与演示样本区分，确认使用者和保留需求 |
| 下载的外部源码和压缩包 | 从测试输入中分离，按是否仍需排查第三方问题决定去留 |

本次仅统计文件数量和体积，没有读取或汇总其中实际账号信息、聊天内容，也没有进行删除。

## 9. 建议的执行顺序与验收标准

| 阶段 | 工作范围 | 验收标准 |
|---|---|---|
| A：建立可靠基线 | AutoMapping 契约、配置缺省行为、mock 配置依赖、收藏重载、私聊整套超时 | 干净副本首次运行结果可解释；失败各有明确归属，避免靠已有本地配置或跳过掩盖 |
| B：只整理位置和公共准备 | 按业务域移动；提取已确认重复的 engine factory；统一资源关闭 | 用例清单和行为范围保持可核对，移动本身不改变产品预期 |
| C：精简脆弱断言 | 签名 hash、精确布局、源码字符串和临时重构约束逐条判断 | 保留下来的约束有理由；被替换的行为有对应断言；移除项有明确失效依据 |
| D：整理人工资产 | 4 个可自动化文件及其工具依赖、交互脚本命名、旧路径和试验文件 | 自动化与人工入口清楚；工具和所需依赖一起管理 |

**如果现在只选择一项，建议做 A。** 先修复测试与当前设计之间的失配，下一次开发时才有可依赖的反馈；仅将文件变少无法解决现在已经存在的红灯。

若只想先改善浏览体验，可以先做 B 中的目录归组，并保留现有失败基线，但它不会解决测试健康度问题。本报告没有预设必须删掉多少文件或多少比例的测试。
