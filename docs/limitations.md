# 已知限制

TIYA 是一个仍在演进的个人 AGI 工程 Demo。当前代码已经能够运行，并覆盖了 Agent、任务机、上下文、记忆、群聊关系和 SKILL 等主要链路，但有几项重要能力尚未完成。

这些限制会直接影响安全性、适用范围和扩展方式。在本地运行或阅读架构前，应先了解以下边界。

## Agent 权限管理尚未完成

当前 Agent 可以发现并调用已注册工具，但权限管理模块仍未完成。系统暂时不能针对每一类操作分别配置授权，例如：

- 允许读取某个目录，但禁止写入或删除。
- 允许查询网络，但禁止下载或执行文件。
- 允许某个 Agent 使用工具，禁止其他 Agent 使用同一工具。
- 对高风险操作要求人工确认或一次性授权。
- 根据群聊、私聊、用户身份或任务来源授予不同权限。

配置中的 `AdminList`、`OwnerList` 等字段主要用于 QQ 侧身份和业务命令判断，**不是 Agent 工具权限系统**。SKILL 管理器当前包含少量硬编码路径限制，也不能替代完整的授权模型。

在权限模块完成前，应把运行中的 Agent 视为拥有其 Python 进程和已注册工具所具备的权限。不要向不可信用户开放高风险工具，也不要给 Bot 进程配置超出实际需要的系统权限和凭据。

## 尚未接入真正的运行沙箱

项目目前没有接入真正的运行沙箱，该部分仍处于 TODO 状态。

SKILL 可以动态加载 Python 函数，也可以通过子进程执行附属脚本。虽然现有文件辅助接口会阻止访问配置目录，并限制部分写入和删除路径，但这些规则只覆盖管理器提供的特定接口，无法隔离 Python 代码本身。

当前实现不具备以下沙箱能力：

- 进程、文件系统和网络隔离。
- CPU、内存、进程数和磁盘配额。
- 系统调用或可执行文件白名单。
- 临时环境销毁和不可变基础镜像。
- 对脚本副作用的可靠审计与回滚。

因此，SKILL 和外部工具必须被视为受信任本地代码。不要安装来源不明的 SKILL，不要让 Agent 执行未经审查的脚本，也不要仅依赖 prompt 约束阻止危险行为。

后续合理方向是让权限判断发生在任务创建阶段，让实际工具执行进入独立的受限运行环境，并将授权、执行和结果回传分别记录。但这仍是设计方向，不是当前已提供的功能。

## 私聊链路仍是最低可运行状态

TIYA 当前主要开发和体验重心都在群聊。私聊已经具备最低可运行链路，包括：

- 私聊对象按需创建和空闲回收。
- 基础 Dialog、Agent、Speaker 与 Persona。
- 消息历史、长期记忆和自动保存。
- 通知回复与少量私聊管理流程。

但私聊的交互设计、主动性、关系维护和工具编排都没有达到群聊链路的完成度。群聊拥有更成熟的话题连续性、成员兴趣、群 Persona、发言概率和社区建模，实际体验会明显好于私聊。

项目中已经考虑过更多私聊方向，例如更细致的长期关系阶段、主动联系策略、跨会话任务延续、用户级权限与隐私边界，但目前尚未实现。文档中的群聊与私聊共用架构表示它们复用了底层组件，不表示两条产品链路已经达到相同成熟度。

## 记忆架构仍然偏厚重

当前记忆模块覆盖了分桶、版本、证据、递归查询、重排、压缩、拆分、优化、迁移和维护任务。它展示了长期记忆如何增长和自我管理，但也带来了较高复杂度：

- 服务和状态类型较多，理解及调试成本偏高。
- 对简单聊天场景而言，维护流程可能重于实际需求。
- LLM 参与多个维护步骤，成本和失败路径较多。
- 本地文件存储适合单实例 Demo，不适合天然地被多个 Agent 并发共享。
- 多 Agent 对同一记忆的身份、可见范围、写入冲突和一致性支持仍不完善。

因此，目前的 ContextMemory 更接近一个功能完整但偏重的研究型实现，而不是已经收敛的通用记忆基础设施。后续仍需要简化核心模型，并把 Agent 身份、命名空间、共享范围、权限和冲突处理纳入统一设计。

记忆模块已经从 TIYA 中解耦为独立项目：[Ricoz217/CoMe_context_memory](https://github.com/Ricoz217/CoMe_context_memory)。TIYA 保留当前集成版本，用它验证真实聊天场景；独立仓库更适合关注记忆模块本身的设计和后续演进。

## 如何理解这些限制

这些问题不会否定项目当前展示的工程结构，但会限制它的使用方式：

- TIYA 适合在受信任、本地、可观察的环境中作为个人 Demo 运行。
- 不应直接作为面向陌生用户的自主执行服务部署。
- 不应把当前 SKILL 执行等同于安全的代码解释器。
- 不应假设群聊和私聊具有相同完成度。
- 不应假设多个 Agent 可以无成本地共享同一个记忆空间。

文档会尽量区分“已经实现”“当前可用”和“计划方向”，不把 TODO 描述成现有能力。

项目的在线运行方式和应用层会话隔离参见[真实运行与持续演进](real-world-operation.md)。会话隔离减少普通业务串线，但不替代本章所述的权限和沙箱。
