# LLM 通信层升级与兼容重构 PRD

日期：2026-10-25  
更新：2026-10-26  
状态：需求与范围已整理，尚未实施  
适用项目：TIYA_ThenIAskYou_2026

本文记录本次讨论中确认的目标、边界和验收要求。本文交付不包含实现代码，不代表已经完成供应商账户或中转网关的联调。后续工程设计和实现以本文为依据；模块文件名可以调整，职责和兼容要求应保持一致。

## 1. 背景与问题

当前 `src/TIYA/LLM_connect.py` 约 2891 行，同时承担 Prompt/Context 数据结构、工具 schema、图片处理与缓存、供应商协议转换、连接池、流解析、排队取消、上下文提交、容量估算和费用统计。

随着多模态业务引入大量图片，当前每轮重发完整历史和 Base64 的方式会重复传输历史图片；仅有本地缓存无法消除网络重复传输。新增 Responses、Files 和生图能力还会改变请求、响应、上下文续接和文件引用契约，继续向现有方法增加分支将提高维护风险。

现有模块已经被 Agent、Speaker、Dialog、图片识别、Memory 和动态工具广泛使用。升级必须保留旧调用方式，并将新协议的复杂性控制在通信层内。

## 2. 产品目标

1. 保留 `TIYA.LLM_connect` 的公开入口及现有业务调用方式，逐步将内部实现委托到 `TIYA.llm`。
2. 将稳定数据契约、请求编排、供应商协议、文件协议和网络传输分开。
3. 在明确支持的服务上使用 `previous_response_id`，正常续接只发送增量。
4. 将 Files 作为独立 Provider 能力，支持上传后复用图片引用；不支持时回退内联 Base64。
5. 支持 image 2.5 的独立图片生成/编辑，以及 Responses 内建生图工具。
6. 接收文字、工具调用、图片及混合结果，图片在通信层落盘并返回统一对象。
7. 保持本地 TTL 策略，不因通信层升级增加永久保留、引用保护或清理系统。
8. 修正已确认的通信正确性问题，逐项记录行为变化并提供回归证据。

- 将 Memory 或其模型预设自动切换到 Responses。

- 自动改写现有模型预设、密钥或生产配置。
- 与本次通信升级无关的业务重构。

Memory 作为旧 `Chat` 调用方应继续工作，允许运行已有相关回归测试；这不构成对 Memory 的功能改造。既有存档必须保持可读，但不研究或改造 Memory 的存档体系。

## 4. 供应商能力基线

以下为 2026-10-25 核查到的官方协议基线，不等于任意中转网关或账户都具备相同能力。

| 服务与接口 | 历史传递 | 图片复用方式 | 实现注意事项 |
| --- | --- | --- | --- |
| OpenAI Chat Completions | 完整消息历史 | 现有内联方式；其他引用按明确声明的能力使用 | 不把通用 Files 存在等同于支持图片 `file_id` |
| OpenAI Responses | 完整 items 或有效父 response 的增量 | `input_image.file_id` 或内联图片 | 协议格式、保存能力、续接能力分开声明 |
| DeepSeek Chat | 完整消息历史 | 图片 `file` 内容块的顶层 `file_id`，或内联图片 | 不直接套用 OpenAI 的文件内容块结构 |
| DeepSeek Responses | 本地完整历史 | `input_image.file_id` 或内联图片 | 官方为无状态兼容接口，不支持 `previous_response_id` |
| Anthropic Messages | 完整消息历史 | `image.source` 中的文件引用，或 Base64 | 保持现有 Messages 契约；Files 相关版本差异由适配器处理 |
| 独立 Images | 显式图片操作请求 | 平台支持的文件、URL 或内联/表单输入 | 不具有对话历史自动续接语义 |

DeepSeek 不支持的 Responses 参数可能被静默忽略，因此 HTTP 成功和返回 response ID 都不足以证明续接生效。未知网关默认不能假定支持远端续接。

OpenAI Responses 生图需要区分顶层对话模型和生图工具模型；独立 Images 的模型则直接是图片模型。不得将两个模型字段混用，也不自动替用户替换已指定的模型 ID。

```text
TIYA/

└── llm/
    ├── __init__.py
    ├── model.py

    ├── usage.py

    ├── runtime.py
    ├── media.py
    ├── gateway.py
    └── provider/
        ├── base.py
        ├── openai_chat.py
        ├── openai_responses.py
        ├── openai_images.py
        ├── anthropic.py
        └── files/
            ├── base.py
            ├── openai.py
            ├── deepseek.py
            └── anthropic.py
```

文件划分为建议，允许根据实际代码量合并文件；独立 Files 能力和依赖边界是要求。

| 模块 | 职责 | 不承担的职责 |
| --- | --- | --- |
| `LLM_connect.py` | 旧入口、重新导出、旧调用适配、Chat 对话行为 | 不累积供应商格式分支 |
| `model.py` | Prompt、工具、资源、请求、结果、usage 和状态契约 | 不导入 Runtime、Provider 或上层业务执行逻辑 |
| `llm/config.py` | 将预设与服务配置解析、校验为有效通信配置，生成运行时快照 | 不读取/写入 YAML，不创建连接，不探测能力，不导入业务模块 |
| `tool_schema.py` | callable 到通用工具定义，保留旧构造器输出 | 不执行工具，不决定历史和路由 |
| `runtime.py` | 请求快照、发送计划、同步状态、资源准备、恢复和降级编排 | 不复制另一套独立业务历史，不手写各家 wire payload |
| `media.py` | 原件与派生资源、图片转换、输出落盘、上传映射及去重、必要时 renew | 不改变 TTL，不做永久保留或清理 |
| Model Provider | 模型操作的请求编码、响应/事件解析、错误分类、能力声明 | 不修改共享 Context，不执行 Agent 工具 |
| File Provider | Files 请求编码、结果解析、文件引用规则及能力声明 | 不管理业务历史，不决定全局重试和回收 |
| `gateway.py` | 连接池、HTTP、JSON/表单/字节传输、SSE 分帧、取消和关闭 | 不理解特定模型字段，不独立决定逻辑重发 |
| `usage.py` | SQLite 请求账本、用量观察、计价快照和查询汇总；提供旧统计适配 | 不从模型协议自行猜测真实字段，不因记账重试重新生成 |

### 5.1 Files Provider 的定位

Files Provider 与模型 Provider 并列，由 Runtime 组合使用。它不是 `Chat.ask()` 的一种对话供应商，不引入 `api_provider="files"` 来发送对话。

例如 DeepSeek 的 Chat Provider 可以与 DeepSeek File Provider 组合，OpenAI Responses Provider 可以与 OpenAI File Provider 组合，两者共享 gateway。新供应商可以复用协议实现，仅覆盖文件形状、路由和能力；不要求复制整套 Chat Provider。

上传成功的文件引用仅在其有效作用域内使用。不能将 DeepSeek 的 `file_id` 自动交给 OpenAI，也不能因格式相似跨账户或跨网关复用引用。

### 5.2 依赖规则

- 内部模块直接使用新位置的契约，不反向导入 `LLM_connect.py`。
- 原有业务函数由调用方传入，工具执行继续留在 Agent。
- gateway 不导入具体 Provider；响应和事件由 Provider 解析。
- 多个模块共享相同类定义；旧入口重新导出该类，不再定义包装子类或重复类型。
- 保持现有 `httpx` 传输基础；引入额外 SDK 必须有明确必要性。

## 6. 稳定数据契约与兼容层

### 6.1 保留的旧契约

包括现有 Prompt 类型、`ToolInput`、`ToolCall`、`ToolResponse`、`TokenUsage`、`Prompts`、`Context`、`AskTask`、`ChatConfig`、`Chat`、上下文异常，以及 `build_tool_payloads()`、`parse_llm_setting()` 和现有对外图片辅助入口。

保留其 import 路径、已有字段含义、构造方式、方法签名和正常结果行为。新增字段提供兼容默认值。明确批准的正确性修复除外，但必须单独记录。

### 6.2 新增内部契约

| 契约 | 必须表达的信息 |
| --- | --- |
| 请求快照 | 操作类型、模型、参数、内容顺序、工具、配置版本和历史匹配依据 |
| 发送计划 | 使用何种协议、完整/增量输入、父节点、待准备媒体、引用方式和选择原因 |
| 请求结果 | 统一内容、完成状态、结束原因、错误、usage、远端 ID 和协议记录 |
| 媒体引用 | 本地 hash/来源、原件或派生身份、MIME、可用元数据、可选远端引用 |
| 远端文件引用 | 文件 ID、服务端及账户作用域、用途、上传/到期状态、对应内容身份 |
| 续接检查点 | 远端 response、对应历史快照、协议/配置作用域及分支关系 |
| 统一流事件 | 文本、工具参数、媒体进度/结果、usage、结束和错误 |

名字可在实现中细化，但不得使用一个 `None` 或空 `Prompts` 同时表达全部内部状态。

### 6.3 业务投影与协议记录

统一 Prompt 面向业务；Provider 协议记录用于正确回放。两者关联保存，编码时不重复发送。

- 保留原始 item 顺序、调用 ID、不透明 reasoning、签名和原生工具项。
- 原生生图工具不能作为本地 `ToolCall` 交给 Agent 执行。
- 图片内容落盘后使用资源引用，避免在多个 JSON 存档中复制完整 Base64。
- 明确区分无损回放和跨协议业务投影。目标能力不足时不静默丢弃必要项。
- 原有只读取 `TextPrompt` 的调用方不因新功能自动收到生图请求；新图片能力显式启用。

## 7. 配置与路由

### 7.1 配置原则

- 原有 `api_type="openai"` 继续表示现有 Chat Completions 行为；`anthropic` 保持现有 Messages 行为。
- 新增协议和自动策略显式启用，不能因升级而自动迁移已有预设，尤其不能迁移 Memory。
- 分别描述对话协议、服务适配类型、Files 配置和能力覆盖，避免仅凭 URL 或供应商名称推测全部能力。
- 现有 `endpoint` 仍是完整地址，不改变其语义。新路由使用显式服务根地址或独立 endpoint 配置，不任意替换路径或抹掉网关路径前缀。
- 支持同服务范围内的显式备用路由，不自动更换供应商或账户。
- 支持远端文件到期参数配置；未配置时按适配器和平台规则处理，不隐式创建清理任务。
- 价格、日志、代理、连接参数和已有额外模型参数继续可用。
- 允许升级配置文件结构和相应模板、校验器；配置结构不必为旧字段堆叠而冻结。业务侧预设名称和解析调用保持稳定。

### 7.2 必须分开的能力

至少区分：请求协议、远端保存、父 response 续接、图片输入、图片文件引用、文件上传、元数据、列表、下载、删除、生图、编辑、mask、流式结果、原生工具和结构化输出。

能力与服务、模型和路由相关。对已知官方接口提供有依据的默认配置；未知兼容网关保持保守，可显式覆盖。不能仅依赖返回码推断被静默忽略的能力。

### 7.3 选择顺序

先确定能满足请求语义的已配置模型路由，再分别选择历史与媒体传输方式：

1. 已明确支持且检查点有效：父 response ID 加本轮增量。
2. 不具备续接或检查点不可用：使用本地完整历史，通过已配置协议重建。
3. 对本次确实需要发送的图片，优先复用有效文件引用，否则准备上传。
4. 无文件引用能力，或发生可明确降级的文件能力错误：使用现有内联 Base64。
5. 请求语义、图片能力或必要历史无法保留：明确失败，不静默改成无图请求。

Responses 无状态回放加 Files 是有效组合；Files 并不只在 Responses 不可用时使用。独立 Images 操作不自动被转换成普通 Chat 请求。

### 7.4 `parse_llm_setting()` 的职责和返回契约

保留 `TIYA.LLM_connect.parse_llm_setting(preset_name)` 的调用方式，继续返回独立、可修改的 `ChatConfig`。内部委托 `llm/config.py` 解析，不将这个入口改成 Provider 工厂、客户端创建器或直接返回 Runtime。

当前调用方会在解析后修改 `keep_alive`、`logger`、`system_prompt`、`model_params` 等字段，再传给 `Chat.setting()` 或 `Chat(config=...)`；这些操作继续有效。每次解析创建独立数据，不能返回全局缓存的可变对象，嵌套参数、路由、能力和文件设置也不能与原配置或其他调用共享可变引用。

处理链路为：

```text
现有配置系统：读取 YAML、版本识别、结构校验、热更新
    → 取得模型预设、被引用的服务及代理配置
    → llm/config.py：校验引用、解析有效配置
    → parse_llm_setting()：返回可修改的 ChatConfig
    → Chat.setting() / Chat(config=...)：应用调用方覆盖
    → 实际执行时生成一致的运行时快照
```

解析只处理配置，不进行网络请求、上传、历史恢复或供应商能力探测。未知能力通过显式配置和适配器默认值处理。

配置错误提供预设名和字段路径，保持旧入口可处理的异常类别，不返回半成品配置；有效预设不以 `None` 表达缺失必要连接信息。现有部分调用方对 `None` 的防御判断无需删除。

### 7.5 新配置结构：服务连接与模型预设

服务连接负责鉴权、代理、网络参数、协议路由、Files 适配及服务级能力；模型预设负责模型 ID、使用协议、上下文预算、生成参数、价格和发送策略。同一个服务可以被多个模型预设复用，Files 无须在每个预设中重复配置密钥。

保留 `LLM_List` 以及预设顶层的 `preset_name`、`model`、`max_context`、`auto_compress_rate`。现有 `get_llm_list()`、按名称查找，以及 Memory 的 `get_llm(name).max_context` 不需要改业务代码。其他配置可按版本组织，不要求旧的扁平网络字段与新服务引用永久共存。

结构示意如下；字段名称可在工程设计中统一，但职责分组、旧读取兼容和覆盖规则是要求。示例中的 endpoint 均为完整路由地址：

```yaml
LLM模型配置:
  schema_version: 2
  Services:
    example-service:
      token: replace-with-your-api-key
      proxy_mode: GlobalProxy
      client_params: {}
      routes:
        chat_completions:
          provider: openai_chat
          endpoint: https://example.com/v1/chat/completions
        responses:
          provider: openai_responses
          endpoint: https://example.com/v1/responses
          capabilities:
            continuation: false  # 未验证网关不假定具备远端续接
        files:
          provider: openai_files  # 也可以是 deepseek_files / anthropic_files
          endpoint: https://example.com/v1/files
          upload_options:
            purpose: user_data
        image_generations:
          provider: openai_images
          endpoint: https://example.com/v1/images/generations
        image_edits:
          provider: openai_images
          endpoint: https://example.com/v1/images/edits
  LLM_List:
    - preset_name: MAIN
      service: example-service
      api_type: responses
      model: your-vision-model
      max_context: 128000
      auto_compress_rate: 0.7
      parameters:
        stream: true
      history:
        mode: auto
      media:
        mode: auto
      price: {}
```

示例不要求每个服务配置全部路由：单独 Chat 服务、单独 Files 能力和单独图片服务均合法。选择的操作缺少必要路由时明确报错，不将未配置路由视为已经支持。

Files 通常继承所选服务连接；如网关的文件路由使用不同鉴权，必须支持在路由范围明确覆盖连接信息，并校验它与模型路由的文件作用域是否兼容。不同服务间不能仅靠引用另一个 Files 连接就假定文件互通。

远端文件过期选项放在 Files 上传设置中；图片模型及价格属于模型/操作配置；Responses 顶层对话模型和内建工具的图片模型分开。新结构不要求生图预设填写无意义的对话窗口参数。

### 7.6 返回对象与字段覆盖

`ChatConfig` 保留旧字段，增加服务路由、Files、能力和发送策略等所需字段；有效主路由继续投影到旧 `endpoint`、`token`、`api_provider`，使旧调用方的校验和设置继续有效。

- `parse_llm_setting()` 返回的对象是可修改配置，不是不可变运行时快照。
- 后续修改旧字段必须真正影响有效配置，不能存在一份隐藏的已解析配置将这些修改覆盖回去。
- 手工构造的增量 `ChatConfig(...)` 保留“未提供的字段不更新”语义，旧字段 `None` 仍按原有增量更新约定处理。
- 解析得到的完整模型预设与手工增量配置必须可区分：切换完整预设时，连接、路由、模型参数、价格、Files 和发送策略等预设域整体重新解析，缺失项恢复为该预设的有效默认值，不继承上一预设的残留值。
- 例如从有价格预设切到无价格预设必须清除旧价格，从有 Files 的预设切到无 Files 的预设必须停用旧文件路由。该语义通过完整预设来源/替换意图表达，不能破坏手工 `ChatConfig(logger=...)` 等局部更新。
- logger、keep_alive、system_prompt 等会话控制字段仅在预设或调用方明确提供时更新，不因更换模型预设无条件清空现有会话设置。
- 调用方修改 `model_params` 后，实际请求使用修改后的值；旧接口中参数整体替换的语义不改成不透明的递归合并。
- 在需要兼容别名转换时，显式原生参数与兼容字段发生冲突应报错。
- `false`、`0`、空价格、显式零价格和未配置分别处理，不使用对象真值替代是否提供字段的判断。
- 清空新配置或关闭新能力使用明确的配置值/更新语义，不能被“未更新”规则吞掉。
- 更改主 endpoint、token、协议或模型后，重新计算有效路由与作用域，避免仍使用原服务的续接或文件身份。
- 直接构造 `ChatConfig(...)`、直接传入旧 `Chat(...)` 参数仍然可用，不强制所有调用先注册服务和预设。

旧有 `ChatConfig` 可继续承担兼容的配置更新对象；Runtime 使用的有效快照应是另一明确契约。两者不要因名称相近而混用。

### 7.7 优先级、热更新与校验

覆盖按明确层次处理：适配器安全默认值、服务默认配置、模型预设覆盖、调用方对 `ChatConfig`/`Chat.setting()` 的显式更新。每个字段规定继承、替换或合并规则，不使用统一深合并处理所有内容。

解析时校验预设重名、服务引用、目标路由、操作与模型能力、Files 适配、鉴权配置、参数冲突和字段类型。不能将失效引用静默替换为模板服务或默认密钥。配置诊断不得暴露密钥值。

不缓存可变 `ChatConfig`。如果缓存内部不可变解析结果，热更新应使依赖已变更服务、预设或代理的结果失效。已解析并传给 Chat 的配置按现有显式 `setting()` 模式更新，不借配置热加载直接改写正在执行的请求。

现有 `Configer` 对 `LLM_List` 按旧模板校验并补默认值；升级时应先识别配置版本，再应用对应结构规则。不能在新预设引用服务后，又补入模板 endpoint/token，从而覆盖真实连接。

现有配置系统继续负责文件 I/O、ruamel 注释、写回和观察者；`llm/config.py` 接收配置数据，不反向导入配置全局对象。`config.py` 不为解析 LLM 配置而加载 Runtime、Provider 或网络客户端。

### 7.8 旧配置读取与迁移

- 无新版本标记的现有扁平预设按旧结构读取，保持 Chat Completions/Anthropic 原协议和完整 endpoint 语义。
- 内存规范化旧配置不触发自动写盘或自动选择 Responses；同一新配置文件可以显式保留旧格式条目作为过渡，不能猜测冲突字段优先级。
- 新格式条目禁止同时使用互相矛盾的旧网络字段与服务引用，提供明确错误和迁移说明。
- 持久迁移保留 `preset_name` 及所有业务对它的引用，保留模型、窗口、代理、价格和生成参数。
- 可确定的配置可迁移，不确定的 Files/Responses/Images 路由不得从旧 endpoint 任意猜测；留待用户显式填写。
- 写盘迁移提供备份，校验通过后原子写入，尽量保留注释；重复迁移幂等，不重复创建服务。
- 不重写真实密钥到文档、测试或日志，不将多个不能确定同作用域的服务擅自合并。
- 不修改 Memory 业务代码或替换其预设；对新版配置的兼容由配置访问和解析层完成。

## 8. 上下文同步与提交

### 8.1 状态归属

业务侧继续管理 Context；Runtime 管理该 Context 与远端状态的对应关系。不能只保存一个与历史无关的 `last_response_id`。

关联状态必须可随旧入口的保存、恢复、复制、清空、替换和回滚处理。状态丢失或无效时允许从本地数据重建，不能产生假续接。

### 8.2 兼容现有提交方式

`Chat.ask()` 正常返回前继续提交请求和响应，上层无需新增确认接口。消息、协议记录和检查点一致提交；上层校验失败调用现有回滚入口时同步恢复状态。

只有明确可接受的结果才能推进续接节点。取消、解析失败和仅有 usage 的结果不能作为成功对话提交。已产生的 usage 仍要记录。

### 8.3 状态变化规则

| 事件 | 要求 |
| --- | --- |
| 首次/恢复后请求 | 验证已有状态；不存在有效状态时发送必要的完整历史 |
| 正常追加 | 检查已同步历史匹配，只发送新增项 |
| 工具调用循环 | 保留必要原生项和调用关联，不重复提交工具结果 |
| 回滚 | 恢复匹配的祖先检查点；无法匹配则重建 |
| 修改/删除已同步内容 | 不再沿用包含被修改内容的后继链 |
| 压缩、清空、替换 Context | 重新评估或建立同步起点 |
| 更新系统提示词/工具 | 发送当前有效配置，按协议判断能否复用历史 |
| 切换服务端/账户/模型/协议 | 重新判断兼容，不能盲目复用 ID |
| `Chat.copy(new_context=True)` | 新会话起点，不继承原对话续接位置 |
| 共享同一 Context | 提交有串行保护，不共享可任意改写的游标 |
| 请求中历史被外部修改 | 检测冲突，不将响应误提交到已变化的历史分支 |

不要假定一个现有业务 round 等于一个 API response。检查点应关联实际请求和内容快照。

### 8.4 快照与存档

- 不直接使用 `Context.to_dict()` 生成请求指纹：当前图片序列化可能产生文件操作，usage 复制可能改变 ID。
- 使用无副作用的内容投影比较已发送历史，排除与模型输入无关的统计和临时状态。
- 在开始实际执行时确定历史和配置快照，后续网络操作、解析和计费使用同一版本。
- 新实现能读取旧存档；新增协议状态使用可识别的扩展结构或版本，缺失时可重建。
- 不保证旧程序能够读取含新增类型的新存档，不以静默忽略来掩盖版本问题。
- 不修改 Memory 的存储流程；其现有 Context 调用和旧存档仍保持兼容。

## 9. Files 与媒体处理

### 9.1 Files 操作

File Provider 提供其声明支持的上传、元数据查询、列表、删除和下载操作。某平台没有下载或某类文件不可下载时，返回明确的不支持结果，不猜测接口。

Runtime 决定何时上传和重传；File Provider 处理具体字段、鉴权、路由、表单和返回结构；gateway 执行传输。文件上传不使用模型 JSON 请求的固定 Content-Type。

图片引用编码由明确的服务适配器负责，例如 OpenAI Responses、DeepSeek Chat 和 Anthropic Messages 使用各自格式。

### 9.2 上传映射与并发

- 缓存身份至少覆盖服务/账户作用域、文件内容、用途和派生版本，不能仅按图片名称缓存。
- 同一进程正常运行期间，相同作用域的同一有效资源只上传一次，多个会话并发上传需合并。
- 上传映射支持持久化复用，但它只记录已知远端引用，不负责本地文件保留。
- 账号或密钥切换采用保守隔离；不在存档中保存密钥明文。
- 引用失效时先使该记录失效；原件存在则按预算重传，不能循环使用失效 ID。
- 共享上传与单个请求的取消应有清晰归属，避免一个等待者取消破坏其他调用或遗留无人管理的后台任务。

### 9.3 本地 TTL：以最新决策为准

**完全沿用现有 TTL，不标记永久，不实现引用保留或清理系统。**

- 可以在实际准备或复用已知本地资源时调用现有 renew。
- 不为每轮远端续接强制读取全部历史文件或重新编码 Base64。
- 不扫描当前窗口、历史、检查点或 Memory 来阻止文件过期。
- `Chat.close()`、回滚和清空不主动删除本地或远端共享文件。
- 本地文件已经过期时，renew 不承担恢复文件的职责。
- 远端续接或文件引用仍有效且本轮不需要原件时，本地缺失不应提前阻断请求。
- 确实需要重传/回放且所有可用来源均失效时，给出明确缺失媒体错误；兼容入口按其失败契约返回，不静默省略图片。
- 不承诺任意旧存档的图片始终可恢复。

本节取代讨论中早先提出的永久标记、可恢复上下文引用保护等方案。

### 9.4 三类不同的远端状态

远端 response 记录、Files 文件留存和推理 KV cache 是不同状态。分别处理它们的有效性和失败，不能用其中一个的 TTL 推导另一个，也不能因此改变本地 TTL。

### 9.5 图片处理策略

保留原有识图压缩和 GIF 抽帧能力，但原件、识图派生图、参考图和 mask 的处理策略分别定义。不得对所有输入统一套用 JPEG 压缩。正确传递实际 MIME，支持无扩展名的本地缓存文件。

旧 `ImagePrompt` 的字符串/Base64 和 Path 语义保持兼容；新增显式来源类型避免将 URL、文件 ID、路径字符串和 Base64 混为一谈。

## 10. 生图、编辑与返回图片

### 10.1 两类操作

- Responses：由对话模型调用原生生图工具，保留生成项、图片结果、工具模型和必要回放状态。
- 独立 Images：使用明确的生成或编辑请求，携带 prompt、参考图、可选 mask 和生成参数。

独立图片接口不把整个对话历史任意拼接为一个 prompt，也不伪装支持 `previous_response_id`。新功能可直接使用 Runtime 的单次操作接口，无需创建带历史的 Chat。

### 10.2 输出要求

- 支持纯图片、文字加图片、多张图片和平台支持的流式图片事件。
- 处理 Base64 结果、可下载 URL 或平台支持的输出文件引用，不能把 Base64 当文本输出。
- 返回前将最终图片落入现有本地存储，记录来源、MIME 和可获得的尺寸信息。
- 临时预览和最终结果区分；同一最终图片不能因 delta/done/completed 重复落盘或重复返回。
- 下载、解码和落盘失败返回具体阶段错误，不能声称已经成功接收图片。
- 不重压缩生成原件；识图或预览需要派生图时单独处理。
- 业务投影使用统一图片对象；保留现有 `ImagePrompt` 的兼容路径。
- 不增加 QQ 发图逻辑，不为旧文本调用方凭空构造文本占位响应。

## 11. 工具 schema、参数与协议记录

### 11.1 工具 schema

- 保留 `build_tool_payloads()` 现有输出结构及内部工具说明用途，包括业务依赖的返回说明元数据。
- 内部提取通用工具定义后，由 Provider 包装成各自协议。
- 尊重动态包装器的 `__signature__`、`__annotations__`、工具别名和同步/异步类型。
- 不因切换 Responses 隐式改变原有工具的必填/默认参数语义；严格模式显式处理。
- 不完整或非法工具参数不能静默转成 `{}` 后交给业务执行。
- 原生工具项与业务自定义工具分别识别，不在通信层执行工具。

### 11.2 模型参数

- 兼容已有 `response_format`，为 Responses 转换至相应 `text.format`；token 上限等字段也按协议处理。
- 保留原生参数通道；兼容参数和原生参数冲突时明确报错，不猜测优先级。
- 不跨模型无条件注入现有 `temperature`、`max_tokens` 等默认参数。
- 构造 payload 时不修改调用者配置，嵌套字典也应避免跨 Chat 共享污染。
- 原有额外参数不因迁移被无声过滤；明确不支持的参数给出诊断。

### 11.3 回放信息

按 Provider 保留必要的 reasoning、签名、工具项、结束状态和顺序。现有可见文本字段不足以替代全部协议数据。

参考：[OpenAI 迁移文档](https://developers.openai.com/api/docs/guides/migrate-to-responses)、[Anthropic thinking](https://platform.claude.com/docs/en/build-with-claude/thinking)。Anthropic 本次仍以原有 Messages 兼容为边界，不扩展到托管 Agent。

## 12. gateway、流式、排队和取消

- 保留 JSON 请求和流式请求，并增加 Files/Images 所需的表单或其他平台支持的传输形式。
- SSE 按完整事件分帧，处理空行、注释、多行 data、网络分块和正常结束；不假定 event 行下一行必为完整 data。
- Provider 解析事件语义；统一保留正常结束、截断、拒绝、错误和断流信息。
- 工具参数增量和多内容项按真实索引/ID 汇总；流结束前不执行不完整工具调用。
- 保留现有兼容平台返回非流式 JSON 等必要处理，但不把不完整流误判为成功。
- 同一会话的请求与提交串行；不同会话可并发，不使用全局对话锁。
- 保留 `queue`、`no_wait`、任务 ID、stop、close 等入口语义；避免用 Event 检查代替互斥保护。
- 一次调用的超时预算覆盖等待、资源准备、网络和恢复过程；不能每次重试重新获得完整预算。
- 配置在执行开始时确定，已开始请求不混用后续模型、价格或鉴权配置；排队请求在开始执行时取配置。
- 连接池更新与续接状态失效分别处理。只切换模型不必重建相同网络连接池，但仍要验证续接兼容。
- 取消和关闭需清理任务登记、响应流与相关资源；不能在取消后继续提交结果。

### 12.1 人工中断与服务端取消

本地停止、传输中断和服务端确认取消分别记录，不能用 `asyncio.Task.cancel()` 成功或流已关闭推断远端推理已经立即停止。

- 本地中断立即禁止后续业务内容交付、工具调用提交和续接节点推进，并清理当前请求。取消通常针对当前 HTTP 请求/响应流，不通过关闭整个共享连接池影响其他请求。
- 对普通同步 HTTP 模型请求，通过终止当前请求/响应流实施取消；仅停止读取或退出业务循环不足以保证网络请求已关闭。
- OpenAI 普通同步 Responses 的官方取消方式是终止连接。后台 Responses 支持 `POST /responses/{response_id}/cancel`；后台流断开后任务会继续，因此如果显式启用该模式，应尝试协议取消并检查最终状态。
- 不因需要中断而自动将所有请求改成后台模式，也不因此引入 Realtime、WebSocket 或托管 Agent。本次普通 HTTP Provider 按已验证的取消能力工作；后台模式如启用，需明确配置和能力支持。
- 对本次 DeepSeek Chat、Anthropic Messages 和独立图片接口，没有经确认的单请求远端取消契约时，关闭当前请求并将远端结果标为未确认，不编造 cancel URL。
- 取消请求有界等待；返回成功也需检查目标最终状态。若任务已经完成，保留已完成这一事实，但按本地中断决策抑制后续业务提交。
- 通过代理或中转网关时，不能假定客户端断开被及时转发到上游；不承诺断开瞬间停止算力消耗或计费。
- 内部结果至少分别表达本地停止状态、取消方式和远端终态（如 cancelled/completed/unknown）；旧 stop 入口保持兼容。
- usage 保留已知值；断流未收到最终 usage 时标记未知或估算，不能据此记为零。手工中断不自动触发重试、降级或重新生成。
- `stop` 字符串、输出 token 上限和 reasoning 配置属于请求前的生成约束，不作为运行中动态取消信号。

参考：[OpenAI 后台模式与取消](https://developers.openai.com/api/docs/guides/background)、[Anthropic SDK 的流请求 abort](https://github.com/anthropics/anthropic-sdk-typescript/blob/main/helpers.md)、[DeepSeek Chat 接口](https://api-docs.deepseek.com/api/create-chat-completion/)。其中 SDK 的 abort 证明客户端请求可取消，不构成服务端立即停算的保证。

## 13. 错误、恢复与降级

内部至少区分配置/能力错误、鉴权、限流、连接故障、超时、取消、上下文超限、引用失效、媒体缺失、解析错误、未完成响应、落盘失败和提交冲突。

| 情况 | 策略 |
| --- | --- |
| 有效续接不再可用 | 在必要数据可用时重建一次完整请求 |
| 文件引用失效 | 失效映射；有原件则重传，否则明确失败 |
| 明确不支持文件能力 | 按已配置策略回退 Base64 |
| 仅某份文件损坏 | 不把整个服务永久标记为不支持 Files |
| 限流/短暂故障 | 有界重试和等待，受总预算限制 |
| 鉴权/配置错误 | 明确失败，不通过改协议掩盖错误 |
| 用户取消 | 停止操作，不自动降级再发 |
| 超时/断流且服务端结果未知 | 不把未知完成当成未执行；不推进游标，不盲目重发生成 |
| 解析出部分内容但未完成 | 保留诊断和已知 usage，不作为完整结果提交 |
| Context 已被外部修改 | 明确提交冲突，不误写历史，不无条件重新生成 |

恢复和降级由 Runtime 统一编排，gateway 不做隐藏的逻辑重发。每种恢复路径有明确上限；文件重传、历史重建和路由回退不能形成循环。

内部结果保留明确状态；兼容 `Chat.ask()` 继续提供 `Prompts | None` 及已有必要异常。上下文超限继续能被既有 Agent 识别。新单次接口可直接读取完整错误信息。

## 14. usage 与 SQLite 请求账本

1. Provider 将真实字段解析为统一 usage 明细；gateway 不解析模型 token 字段。
2. 分开处理真实 usage、本地预算估算和价格记账。没有 usage 不等于真实消耗为零。
3. 保留原有 `Prompts.usage`、`Context.usage` 的兼容读取；`LLM_usage` 仅保留必要兼容入口，内部改为逐请求 SQLite 账本。
4. 流式分阶段 usage 按字段语义合并，不能用 `max()` 选择整个对象，也不能重复累加累计值。
5. 已知消耗在失败、取消和回滚时仍记录；历史回滚不回退真实费用。
6. 一次业务调用的各次真实模型请求分别记录，同时有业务调用 ID 和尝试信息，避免重复入账。
7. 支持文本、图片、缓存和原生生图工具的可获得明细；区分对话模型与图片模型，不套用单一价格。
8. 每个请求都保留本地估算/假设值和依据；真实值未返回时不漏账，真实未知字段保持未知，不能将估算改标为真实。
9. 统计写入失败不触发模型重新调用。
10. `previous_response_id` 和文件引用减少网络传输，不代表历史 token 不参与计费或容量计算。

参考：[OpenAI 上下文状态](https://developers.openai.com/api/docs/guides/conversation-state)、[Anthropic 流式 usage](https://platform.claude.com/docs/en/build-with-claude/streaming)。

### 14.1 现有 `LLM_usage.py` 的依赖核查与重写边界

对仓库源码、测试、脚本及 prompt 代码进行静态检索后，依赖如下：

| 调用方 | 实际使用 |
| --- | --- |
| `LLM_connect.py` | 导入 `ApiPrice`、`LLMUsage`、`_GLOBAL_USAGE`；创建价格、更新全局统计和调用传入记录器的 `update()` |
| `memory/engine_runtime.py` | 运行时导入 `LLMUsage`，仅用于预留字段注解；该字段初始化为 None，未找到实例化或更新调用 |
| `memory/llm_pipeline.py` | TYPE_CHECKING 类型导入和可选 `usage_store` 参数，保存后未实际调用该记录器 |
| `memory/multimodal.py` | TYPE_CHECKING 类型导入和可选 `usage_store` 参数，保存后未实际调用该记录器 |
| `tests/test_llm_usage_free_price.py` | 直接使用 `ApiPrice`、`LLMUsage`、`UsageStorage`，覆盖无价格与零价格等行为，并依赖部分内部存储结构 |

没有找到业务模块直接调用 `usage_now()`、`UsageNow`、`UsageStorage`，或外部直接使用 `LLMUsage.overview()/query()/save()/load()` 的情况。模块内部的全局 callback 会更新日志状态栏，这属于现有可见功能，不能因没有外部调用就当作无用代码。

Memory 的实际统计从 `response.usage` 汇总，经其自身 storage 记录；它不是依赖 `LLMUsage` 的内部 JSON 聚合结构。重写不能破坏 `Prompts.usage` 的既有读取，也不借此改造 Memory。

据此，重写统计内部实现的耦合范围较小，可将新实现放入 `llm/usage.py`，旧 `LLM_usage.py` 保留必要的重新导出或薄适配。暂不删除旧导入路径和 Memory 仍导入的类型；不需要为了类型预留字段保留旧内部实现。

已被批准的通信重构可以改用新的统一记录接口；现有 `Chat.usage_record` 兼容入口仍应能适配外部传入记录器。迁出的价格类应保持单一类型身份。测试可改为验证公开结果，不要求继续暴露旧嵌套 `_storage` 布局。

历史 `data/token_usage/usage.json` 仅作为一次性迁移来源和备份，升级后不再作为运行中的账本写入。导入旧累计数据时不能凭空补成过去每次请求的明细，也不因重写默认清空历史。

### 14.2 记账单位、唯一 ID 与长期保存

账本以实际请求为基本单位，不再把 `(model, price)` hash 下的一份日累计数据作为原始事实。

| 身份 | 含义 |
| --- | --- |
| `call_id` | 一次业务调用，从排队、准备、模型请求到恢复过程的关联 ID |
| `request_id` | 一次实际服务请求/尝试的本地唯一账本 ID，重试和重新生成分别分配 |
| 平台 request/response ID | 供应商返回的标识，单独保存，不代替本地 ID |
| `observation_id` | 同一请求上的一次用量观察或修订，关联 request_id |

- 本地 ID 可使用 UUID 并由数据库主键/唯一约束保证唯一性；不依赖模型名、价格、日志文本或易碰撞的时间字符串。
- 现有 `AskTask.id`、`TokenUsage.id` 和账本 request_id 分别表达任务、用量对象和实际请求，保留关联，不因为复制/相加用量对象而生成新的请求账目。
- 每次实际发送前先分配并持久化 request_id、身份快照、时间、初始本地估算和准备状态，然后交给 gateway。不能等拿到真实 usage 才记账。
- 请求重试有独立 request_id，共享 call_id，记录尝试序号和前一请求关系；同一次流的多个 chunk 不创建多个请求。
- 排队取消、配置错误、图片准备失败等未发送情况仍有 call_id 和阶段记录，明确标为未发送，不虚构已发生的远端用量。
- Files 上传、查询、下载、删除，以及显式取消/查询响应等服务操作记录各自操作类型和请求身份；不适用 token 的操作标为不适用，不混成模型 usage 缺失。
- 请求、观察、计价快照及历史导入记录长期保存，不参与图片 TTL，不设置自动过期或自动清理。
- 请求事实和用量观察保留审计关系。重复通知或回调不重复入账；更正通过新观察/修订保存，已保存的真实观察不能被后来的估算覆盖。
- 新内部结果和日志提供 call_id/request_id；旧 `Chat.ask()` 不因失败需要返回 ID 而改变 `Prompts | None` 契约。可通过任务关联、账本查询或新增诊断接口检索失败记录。

### 14.3 真实、估算和汇总选值

这里的“真实”指供应商实际返回的 usage（reported），不等同于已与供应商账单完成对账。旧 `verified` 标记经兼容适配后表达来源，不能继续暗示账单已核验。

每次请求分别保留：

1. **供应商报告值**：原始 usage、规范化值、来源事件、完整性及可获得的响应标识。没返回的字段为 NULL/未知，不能填真实 0。
2. **本地估算值**：发送前的输入/输出假设，及过程中或结束后基于已知输入、已接收输出、图片元数据计算的修订。记录算法版本、参数、假设和完整性；真实值已返回也不删除估算。
3. **用于汇总的有效值**：对每个可独立解释的用量字段，优先选择最新有效的报告值，没有报告值时使用最新有效估算，同时保留来源标记。

因此同一请求允许真实与估算并存，但默认总量不能把它们相加。流式多个累计 usage、重复完成事件和估算修订也不能重复累加。

例如某请求本地估算输入 1000、输出 100，平台只报告输入 950：默认汇总使用输入 950（reported）和输出 100（estimated），保留原来的估算输入以供核对，并标记结果来源混合。平台明确报告输出 0 时则使用真实 0，不当作缺失。

具体约束：

- 估算应描述其测量范围，区分全量估计、已接收内容的下界和待完成假设。
- 断流时接收到 0 个输出 token 只能说明本地观测为 0，不能证明服务端未进行 reasoning 或生成。以此给出的估算必须标为下界/不完整。
- 对未知 reasoning、图片或缓存量仍保存本地假设及依据，不能捏造 reported 值；无法可靠覆盖的维度显式标为未覆盖。
- 本地假设包括 0 时，也记录假设和不确定性，避免把假设 0 与真实 0 混淆。
- 不根据“上一轮历史长度”自动声称本轮缓存命中；缓存估算假设单独注明。
- token 总数与其文本/图片/缓存等细分可能存在包含关系，规范化和计价需声明包含关系，不能作为独立消耗重复求和。
- 旧 `Prompts.usage` 可投影有效值，新契约增加来源、完整性和账本关联；不能因为旧类型只能装数字，就丢弃原始来源证据。

### 14.4 模型、预设与价格身份

需要替换当前仅按模型字符串和价格 hash 识别的方式。至少保存以下当次身份快照：

| 类别 | 必要信息 |
| --- | --- |
| 预设 | 可选稳定 preset_id、当时的 preset_name、配置版本/指纹 |
| 服务 | 可选稳定 service_id、服务名称、适配类型、脱敏路由、账户作用域标识 |
| 模型 | 请求的模型 ID、平台实际返回的模型 ID（如有）、协议和操作类型 |
| 关联 | call_id、request_id、尝试关系、可选会话/外部任务标识 |
| 价格 | 当次价格版本/快照、币种、单位、各计价项和未配置状态 |

- 新配置可提供稳定服务/预设 ID，迁移时可一次性生成；改名保留 ID。解析函数不能每次生成新的预设身份。
- 没有稳定 ID 的旧配置保留名称与当时快照，不假定能自动追踪改名历史；每次请求的唯一性不依赖这些配置 ID。
- 同名模型在不同服务、账户、协议或预设下可分别查询。通过修改汇总分组查看合计，不通过强行合并原始身份实现。
- 更新预设、切换服务、修改价格或删除配置，不回写旧请求的身份和成本。
- 配置实体删除不能级联删除账本；历史快照与当前配置对象的生命周期分离。
- Responses 生图的对话模型和图片模型分别记录用量/计价组成，并关联同一请求，不能全部记在主模型名下。
- 价格和用量契约放入 llm 的稳定契约范围，旧 `ApiPrice` 保留必要适配，但不能要求所有新增计费维度塞入其三个单价字段。
- 不存储 API Key 明文、带密钥的 URL 参数或请求头；身份指纹仅覆盖适当脱敏后的配置。

### 14.5 费用计算与更正

- 费用依据当次价格快照计算，保存其使用的用量来源和公式/版本。reported token 加本地价格得出的费用仍是本地计算值，不能冒充平台实际扣费。
- 分开汇总完全基于报告值的费用与包含估算的费用，并提供有效费用视图；不同币种分别显示，不自动兑换或相加。
- 未配置价格的金额为未知，不是 0；显式零价格计算为 0。
- 使用 Decimal 及明确精度的定点存储或十进制字符串计算，不以二进制浮点累计账目金额。
- 缓存的零单价不能因 truthiness 判断自动替换为普通输入单价。
- 生图和其他操作按各自计价项计算，防止总量和细分、主模型和工具模型的重复计价。
- 晚到的真实 usage 或更正重新计算有效费用并留下修订关系，不额外生成一笔相同请求消耗。已完成的历史账目不因当前配置价格改变而重算。

### 14.6 SQLite 存储与可靠性

SQLite 是唯一运行中账本，建议数据库位置为 `data/token_usage/usage.sqlite3`。内部可使用 JSON 字符串保存原始 usage 或快照扩展字段，但不再维护 JSON 账本文件。

建议逻辑表如下，物理表名和适当合并由工程设计确定：

| 逻辑表 | 用途 |
| --- | --- |
| calls | 业务调用、排队/准备结果和请求关联 |
| requests | 每次服务请求、身份和配置快照、时间、执行与远端状态 |
| usage_observations | reported/estimated 观察、字段范围、版本、依据和原始数据 |
| price_snapshots | 当次价格方案、币种、单位和版本 |
| charge_revisions | 根据观察和价格得到的费用组成与修订 |
| legacy_totals / import_batches | 旧累计数据、导入来源、幂等标记及对账结果 |

执行要求：

- 使用事务、主键、外键和必要唯一约束，防止孤立观察、重复请求和重复修订。
- 请求状态、最终观察及相应费用修订在明确事务边界提交。
- 沿用项目合适的 SQLite 连接管理、WAL、busy_timeout 和 schema 版本约定，阻塞数据库操作不阻塞事件循环。
- 账本用于长期记录，明确提交与同步策略；连接关闭等待必要写入完成，不能仅依赖尚未落盘的内存队列。
- 按时间、服务、预设、模型、状态和 call_id 建立必要索引，查询分页；日志不扫描全量历史。
- 发送前的初始记账失败则不开始新的远端调用，明确暴露账本错误，不能静默发送后丢账。
- 网络已经执行后的最终写入失败只重试记账，不重试模型生成；初始账目保留 pending/未完成状态，向诊断暴露未结算事实。
- 启动恢复未结束记录时标为 interrupted/remote_unknown 等实际可证明的状态，不能直接认定请求未发生、费用为零或自动重发。
- 本地提交和远端请求不能组成原子事务。发送边界崩溃时保留未确认事实，不宣称远端 exactly-once 或凭 ID 即可防止上游重复生成。
- 长期保存不等于保存完整 prompt、图片或全部流事件；默认账本只存用量证据、计价和必要元数据，避免账本变成内容副本库。

### 14.7 写入、查询和日志接口

核心写入接口需要调整，不能继续只依赖 `update(model, counts, price, verified)`：缺少 request_id 和生命周期时，无法区分重复通知、估算修订和新请求。

建议语义接口（名称待工程实现统一）：

```text
begin_call(...) -> call_id
begin_request(call_id, identity, estimate, ...) -> request_id
observe_usage(request_id, source, values, observation_key, ...) -> observation_id
finish_request(request_id, outcome, remote_state, ...) -> request_record
get_request(request_id) -> record
query_requests(filters, cursor, limit) -> page
summarize(period, filters, group_by, basis) -> summary
```

- 写入接口携带请求身份和幂等信息，真实报告、估算及结算分别表达。
- 查询支持 reported、estimated、effective 三种来源视图；effective 是逐字段择优视图，不能相加前两者。
- 汇总提供请求数、成功/失败/取消/未确认数、真实与估算覆盖、token、分币种费用和未知价格数量。
- `overview()` / `usage_now()` 可保留薄适配，但不保留旧嵌套字典作为核心查询格式；新的分页查询以单条请求记录为主。
- 兼容 `LLMUsage.update()` 的调用可转为账本记录；未提供稳定 request_id 的旧调用不能被假装具备自动幂等性，内部新链路必须使用新接口。
- `Chat.usage_record` 的多个接收器共享同一次请求身份，不因为记录到多个视图而在全局账本重复收费。
- 日志是账本的订阅者/查询视图，在提交后更新状态栏；日志 callback 失败不撤销记账、不触发远端调用。
- 月度日志可显示有效 token/费用及估算标记，保留现有简洁状态栏用途；不要求业务为了日志读取复杂账本结构。
- 不改造 Memory 自身统计存储；继续满足其 `response.usage` 的旧读取，额外来源信息保持可访问。

### 14.8 JSON 历史迁移

- 先备份并冻结旧 JSON 写入，再以可重复安全执行的事务导入 SQLite；正常运行不双写 JSON。
- 按旧 `storage` 导入历史累计余额/统计记录，不将它伪造成逐请求记录；这些导入项也有唯一 ID 和来源标识。
- 旧文件缺失的 preset、服务、实际请求次数、每次请求 ID 和完整价格维度保持未知，不按名称猜测补造。
- `last_record` 可能是已有累计中的最近记录，不能当作额外消耗再次累加。
- 导入有来源和稳定条目标识，重复执行不增加金额或 token。来源变更时显式校验，不将变更后的全量文件再加一遍。
- 迁移核对分日期、模型、来源类别、价格与币种的 totals；新查询分开标明历史累计与新逐请求数据。
- 新的请求数量统计不把历史累计行数当成旧请求次数。
- 成功导入后保留原文件备份，不为新记录继续写入旧文件；失败可回退且不影响原数据。

本节以用户 2026-10-26 的 SQLite、逐请求真假来源、唯一 ID 和长期保存要求为准，替代此前仅按日累计统计的方案。

## 15. 正确性修复与行为变化记录

用户已允许修正相关问题。以下为静态核查得到的优先回归项，实施时先复现并记录，再修复；不扩展为无关代码整治。

| 项目 | 新行为要求 |
| --- | --- |
| 取消/异常返回仅有 usage 的 Prompts，外层仍可能提交 | usage 与成功状态分开，失败不提交对话 |
| 提前返回漏记 usage | 统一完成记录路径，保留已知消耗 |
| `run()` 与 `post_nowait()` 修补提交不同 | 共用规范化与提交规则 |
| Anthropic 分阶段 usage 用整个对象比较 | 按协议语义合并字段 |
| 损坏工具参数回退为空字典 | 标记解析失败，不伪造有效工具参数 |
| 未完整识别结束状态和原生内容顺序 | 记录状态和有序内容，避免部分结果误提交 |

| 排队前检查不能反映执行时上下文 | 实际执行时以确定快照做最终检查 |

| 新链路中缺图仍继续无图请求 | 返回明确缺失媒体失败 |

每项提供变更前触发条件、变更后结果和对应验证。现有工具闭环修补属于已被测试依赖的行为，应先保留，再明确任何必要变化。

## 16. 性能与可观测性

- 正常远端续接时，历史图片不重新上传、不读取其完整 Base64；只准备新增或确实失效的资源。
- 无续接但有 Files 时，历史图片通过小型引用传输，不重复内联内容。
- Base64 回退保持必要的现有语义，但内存缓存有大小边界，不随整个进程使用历史无限累积。
- 图片转换和阻塞文件操作使用现有适当执行器，上传并发有界。
- 日志记录操作、模式、路由选择原因、图片数量、上传/复用次数、请求体大小、重试原因、耗时和结果状态。
- 错误保留 HTTP 状态、平台错误码及可获得的 request ID，避免仅剩通用 HTTPError。
- 不将密钥、完整 Base64、巨大图片内容或完整敏感请求写入诊断日志。
- 不预设固定性能提升倍数；用相同样本测量传输量与上传次数，并记录重建成本。

## 18. 实施顺序与完成标准

1. **建立基线**：确认旧接口与现有测试，增加必要的协议样本和错误复现；不改现有生产预设。
2. **迁出契约与 schema，建立配置解析层**：保持旧入口重新导出和 `parse_llm_setting()` 返回契约；完成新旧配置读取、覆盖和版本校验，验证动态工具和序列化。
3. **提取 gateway 与现有模型 Provider**：保持 Chat Completions/Anthropic 正常行为，逐项修复批准的问题。
4. **独立 Files Provider 与媒体链路**：OpenAI、DeepSeek、Anthropic 适配、引用映射、去重、失效和 Base64 降级；TTL 不变。
5. **加入 Responses Runtime**：完整回放、有效续接、检查点、回滚和恢复，不迁移 Memory。
6. **加入两类生图操作**：独立 Images 与 Responses 工具，图片结果统一落盘。
7. **SQLite 请求账本与集成验收**：完成逐请求身份、真实/估算观察、计价和历史导入；运行适当旧回归、验收矩阵和有条件的真实接口验证，记录兼容例外及行为修复。

阶段可独立评审和回退，但首期最终交付必须包含 Files、`previous_response_id`、两类生图与图片接收链路，不能仅完成文件拆分就判定升级完成。

完成时至少提交：新模块、旧入口兼容层、测试与脱敏样本、配置说明、能力表、行为变化记录，以及实际完成和未完成的集成验证结果。业务上启用新策略使用显式预设配置，原 Chat Completions 路径继续可用。

## 19. 当前风险与验证边界

- 兼容网关可能只实现部分格式，或静默忽略字段；需要能力配置和实测，不能凭接口名称推断。
- 文件和 response 引用失效而本地 TTL 已清理原件时，恢复可能失败；这是本次明确接受的边界。
- 跨协议不能保证不透明 reasoning、原生工具和图片历史的完全等价；必要信息无法保留时明确失败。
- 图片输入和生图存在模型及账户能力差异；支持协议不等于当前账户能调用全部模型。
- 新功能涉及共享底层模块，Memory 虽不迁移，旧接口回归仍不可省略。
- 所有真实配置保持原样；本 PRD 中的官方能力核查尚未替代生产网关联调。

截至本文版本，已知需要用户确定的范围取舍均已获得答复，没有阻止继续细化工程设计的未决产品问题。发现新的实际协议差异或会扩大业务范围的需求时，应重新明确边界，不自行扩张本次工作。
